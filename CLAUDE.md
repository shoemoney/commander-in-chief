# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Commander In Chief is a deterministic twin-stick vertical run-and-gun (modern *Ikari Warriors* remake) on **Godot 4.7 / GDScript**. The repo is currently at the **P3** milestone — playable start→finish, and past greybox: the art is owned procedural sprites (`tools/gen_*.py`) plus bespoke generated boss/vehicle/desert pieces over a Kenney-CC0 FX base (see `assets/art/`, `assets/cc0/`). The entity bakes it used to ship are gone from the tree **and from git history** — every commit was rewritten on 2026-07-27, which cleared the last open-source blocker (the tool that did it is not shipped — the job is done and it enumerated the retired vendor paths). The repo is now **public** and shipped **v0.3.0** (macOS/Linux/Windows binaries). ⚠️ Any clone predating that purge is on rewritten history and must be re-cloned. (`ASSETS.md`) `docs/PLAN.md` is the full P0–P7 production plan (much of it aspirational). **The sim code is the source of truth for what actually exists** — don't assume a feature described in the plan or README is implemented.

## Commands

Godot lives at `/Applications/Godot.app/Contents/MacOS/Godot` (universal binary, native on Apple Silicon). All commands run headless except the editor and screenshots.

```sh
# Run the game in the editor
/Applications/Godot.app/Contents/MacOS/Godot --path .

# Import assets — REQUIRED once after cloning, and after pulling ANY new
# class_name script (Godot's global class cache must re-scan). CI does this.
godot --headless --path . --import

# Full test suite — USE THIS when anything else may be running (parallel worktrees /
# concurrent agents). (~23 s. Do NOT trust any count written down here — it grows constantly.
# The `PASS —` line prints the live pair; methods are also countable without running Godot:
#   grep -hE '^func test_' tests/test_*.gd | wc -l   minus test_perf.gd, which is opt-in.
# README.md quotes the method count and test_assets.gd FAILS if it drifts, so adding a
# test means updating README.md in the same commit.)
# tools/run_tests.sh owns the shutdown-leak gate (see the user:// note below).
tools/run_tests.sh                          # full suite
SUITE=mechanics tools/run_tests.sh          # single suite, filter by filename substring
tools/run_tests.sh -s res://tools/smoke.gd  # any other headless script

# Same suite with raw Godot (NOT recommended — no leak gate, only use if alone):
# godot --headless --path . -s res://tests/run_tests.gd
# SUITE=mechanics godot --headless --path . -s res://tests/run_tests.gd

# Sim determinism lint — the no-floats/no-RNG/no-Time/no-scene-tree gate.
# NOT part of the suite; only CI runs it, so run it yourself after sim edits.
tools/run_tests.sh -s res://tools/lint_sim.gd

# Signature-moment screenshots (dev tool; needs a GL context — X or Xvfb)
SHOT_DIR=/abs/path godot --path . --rendering-method gl_compatibility \
    -s res://tools/screenshots.gd
```

**Running a single test suite:** set the `SUITE` env var to a substring of the suite filename (e.g. `SUITE=mechanics`) — the runner filters its `TEST_SCRIPTS` array on it. Each suite is a plain `RefCounted` whose `test_*` methods assert via the `Runner.T.ok/eq` helpers (no GUT addon). ⚠️ A runtime error mid-method silently aborts that method's remaining assertions without failing the run — hold dict references across `sim.step()` (dead entities are swept from the sim arrays).

**Two ratchets guard the "green but wrong" failure mode — don't neuter either:**
- **Engine-error gate** (`run_tests.gd::_gate_engine_errors`). Godot's own `ERROR:` lines fail nothing on their own, and the suite was printing ~400 of them while reporting PASS. The runner now reads its own engine log back (`user://logs`, enabled by `debug/file_logging` in `project.godot`, debug builds only) and fails on any un-allowlisted `ERROR:`. `ERROR_ALLOW` is deliberately near-empty — one narrow entry today (`"ConfigFile parse error at user://"`, so the save-robustness tests can write a deliberately corrupt config — the parse error IS the scenario) — fix the cause, and only add an entry with a written justification. If the gate reports "no log carried this run's marker", that's parallel Godot processes rotating the log away: run ONE.
- **Stub parity** (`tests/test_stub_parity.gd`). Every `main.<x>` / `main.get("<x>")` that `src/view/menu.gd` and `src/view/hud.gd` execute must exist on every hand-written `main` stub the headless tests hand them. A missing field aborts the reading call, the row measures as ABSENT, and every assertion still passes — which is exactly how the c4-18 `last_run_score` gap shipped. Add a `main.` read to a view script and you add the field to the stubs, or the suite goes red.

## Architecture: the sim/view split

This is the one thing you must internalize before touching code. Everything the game *is* lives in a deterministic, render-free core; the scene tree is only a view over it.

- **`src/sim/`** — the deterministic core. `SimWorld.step(inputs)` advances the entire game exactly one 60 Hz tick, calling its subsystem steppers in a fixed order (players → tanks → projectiles → enemies → bunkers → spawner/boss/colossus/gates/camera/observer). State is plain `Array[Dictionary]` (no node objects). `Fixed` is 16.16 fixed-point math; `SimRng` is a seeded xoshiro128**. **No floats, no engine RNG (`randi`/`randf`), no `Time.*`, no scene-tree access may enter `src/sim`** — that is what makes the sim bit-identical across x86_64 and Apple Silicon arm64.
- **`src/main.gd`** (+ `src/view/art.gd`) — the *only* view. It owns all floats, reads sim state, and draws. `_physics_process` calls `sim.step(_gather_inputs())`. The float→int boundary is `_quantize_axis` → `SimInput` axes clamped to `[-256, 256]`; the sim never sees a raw float.
- **`SimWorld.events`** — transient per-tick view triggers (`explosion`/`kill`/`gate_open`/`vest_break`/`victory`/…), rebuilt every `step()` and **excluded from the checksum**. This is the decoupling seam: the sim emits events, `main._consume_events()` turns them into screen shake / hit-stop / flash / particles. The sim never knows feel exists.

### Determinism is enforced by a golden-checksum test — read this before editing the sim

`SimWorld.checksum()` is an FNV-1a hash over the full ordered sim state. `tests/test_determinism.gd` runs a scripted 60 s 2P torture input and asserts the sampled checksums equal committed `GOLDEN` values.

**Any change to sim logic, state fields, or the order state is hashed/stepped will change these checksums and fail `test_determinism.gd` — by design.** When the change is intentional, re-record: set `GOLDEN` to `[]` to make the test print the new values, run it, paste them back, and note *why* in the comment (see the existing P3 re-record note). Do not re-record to make a red test go green without understanding what moved. Per the plan, behavior changes only at phase boundaries.

The same discipline applies to `checksum()` itself: if you add a sim field that affects gameplay, add it to the checksum (and expect to re-record goldens).

### Netcode

`src/net/lockstep.gd` (`LockstepSession`) is transport-agnostic deterministic lockstep: both peers run the same `SimWorld`, only encoded `SimInput` crosses the wire (`input_delay`-ticks ahead), the sim advances only when both players' inputs for the next tick are present, and checksums are exchanged every 60 ticks for desync detection. A real transport (Steam Networking Messages) is *meant* to plug into `on_send` / `receive_remote_input` without touching the loop.

⚠️ **It is a design sketch, not shipped netplay.** ~260 lines, **zero production callers** — nothing in `src/main.gd` or the menus ever constructs a `LockstepSession`, and no transport exists. **The test suite is considerably more adversarial than this file used to claim** (it said "latency jitter only: no packet loss, no duplication, no disconnect/timeout path", and that was wrong on the first two — corrected 2026-08-23 against the code): `FakeWire` schedules deterministic packet **loss** (`drop_every`) and **duplication** (`dup_every`) on top of jitter, and the suite covers loss-survival — *with a control proving the test can fail* — duplicate/reorder idempotency, first-write-wins on conflicting duplicates, malformed-input rejection, handshake mismatch, stall-without-remote-input, and corruption→desync detection. What it is **not** is a network: everything is in-memory on a fixed no-RNG schedule, there are no sockets, and there is deliberately no ack/resend/timeout or disconnect path (`src/net/lockstep.gd:19,28` — lockstep doesn't need one). So the suite shows the sim is deterministic enough for lockstep and that the loop's stall/catch-up/desync logic is self-consistent — it still says nothing about a real lossy network. Don't describe online co-op as working. (The understatement mattered in the one direction docs rarely get audited for: a doc that *undersells* its own tests invites an agent to go rebuild coverage that already exists.)

## Conventions & gotchas

- **Modes**: `SimWorld._init(seed, player_count, mode)` where mode is `"campaign"`, `"arcade"`, `"endless"` or `"boss_rush"` (sim_world.gd:741). `main.gd` hard-codes seed `0xC0FFEE`; F2 toggles 2P, F3 toggles Endless War, R restarts.
- **Fixed-point**: multiply/divide via `Fixed.mul`/`Fixed.div`, never `*`/`/` on two fixed values directly. Constants suffixed `_TICKS`/`_RAW` are not fixed-point; everything else in the sim is.
- **`.gd.uid` files** are Godot 4.x script-UID sidecars — committed, machine-generated, don't hand-edit.
- **Assets**: `assets/cc0/` is CC0 (Kenney), now mostly the FX base rather than stand-in greybox; `assets/art/` is owned art — procedural sprites regenerable from `tools/gen_entities.py` · `gen_ui_chrome.py` · `gen_ui_icons.py` · `gen_ui_glyphs.py` · `gen_fx_cards.py`, **plus** ~14 generative-AI files (tank/gunship/colossus bodies+barrels, cacti, scrub, tumbleweed). `ASSETS.md` carries the per-subfolder provenance table. `.import` files are generated on `--import`. (Generative-AI assets are allowed — the earlier no-AI policy was dropped.)
- **Two draw-time ARBITERS own screen space — route through them or you silently reintroduce the bug they killed.** `main.band_rows()` arbitrates the stacked HUD message bands; `main.claim_label_slot(rect, taken)` arbitrates every *world-space* string (crate prices, identity labels, kill toasts, objective signage). Both have ratchets, and both are bypassable by simply drawing directly — which is exactly what happened: `claim_label_slot` shipped once as a signature, a docstring and `return rect`, called only from its own test, so the check went green while the screen still stacked text into "an unreadable boxy clump over the player soldier". The rule for world labels: build the rect, pass it through `claim_label_slot` with the frame's `_label_slots`, append the result, then draw the plate AND the ink at the returned position (drawing the plate at the claimed rect and the text at the old baseline is how you get a label sitting beside its own background). Anchored signage reserves its pixels first and never moves; transient combat text yields. `_label_slots` is cleared at the top of `_draw()`.
- **A "hanging" test suite is almost always CPU contention, not a slow test.** The full suite runs in **~23 s** (~1,150 methods / ~37.4k assertions — measure, don't quote: assertion totals differ per platform, and both numbers grow every cycle). If it appears to stall — output freezing mid-run, a suite that never prints its `PASS —` line — check `ps aux | grep -c '[G]odot'` first: parallel sessions/worktrees each running Godot starve each other, and a starved run sits at <1% CPU making no progress. `pkill -f Godot` and run ONE. Verified 2026-07-24: a "stall" blamed on `test_localization.gd::test_shipped_font_has_real_cjk_glyph_coverage` was pure contention — that test measures at **21 ms**, and localization/hud/perf/soak are 0.7/0.5/1.5/0.4 s each.
- **A fresh worktree stalls on a COLD IMPORT, and it looks exactly like the contention stall above — but `pkill` is the wrong fix.** A new `git worktree` has no `.godot/`, so the first Godot run does a full asset import: zero output, <1% CPU, several minutes, then either a wall of `Identifier "SimWorld"/"Fixed" not declared` parse errors or nothing at all. Six independent agents hit this on 2026-07-25 and several reached for `pkill -f Godot` (the remedy for the *other* stall) before finding it. **Run `godot --headless --path <worktree> --import` once before the first test run** — or `cp -R <main>/.godot <worktree>/` to start warm. Tell them apart by CPU: contention = many Godot processes each starved; cold import = one process, machine otherwise idle.
- **A THIRD stall: a script that ABORTED, leaving the SceneTree spinning with no main loop.** One Godot process, ~1% CPU, indefinite runtime, no output — indistinguishable at a glance from the cold-import stall, and it also looks like a slow/frame-paced probe. It is neither: an error inside `_init` (a bad dict key, in the observed case) kills the script before it installs a main loop, and the engine keeps running forever with nothing to do. Verified 2026-07-25 — the same probe, once fixed, ran **4,000 sim ticks in 1.87s at 97% CPU**, so a healthy headless sim run is CPU-BOUND. **Low CPU in a headless run means broken, never slow.** Tell the three apart: many starved procs = contention (`pkill`); one proc on an idle box with no `.godot/` = cold import (`--import`); one proc, low CPU, `.godot/` present = read the script's own stdout/stderr for an `_init` error before assuming anything about speed.
- **A FOURTH stall, but only a new TRIGGER — an incompatible method-override return type — for the THIRD class's mechanism, not a new one.** One Godot process, <1% CPU, indefinite runtime, zero output — another doppelgänger of the cold-import stall. Measured behaviour is the opposite of "silent": when an override changes a base method's return type (e.g., `_verb_line(...) -> float` overriding a base `_verb_line(...) -> void`), the parse fails fast and loudly — the headless run's own stdout prints `SCRIPT ERROR: Parse Error: The function signature doesn't match the parent. Parent signature is "_verb_line(int) -> void".` followed by a GDScript backtrace naming the `_init` frame. Whether it hangs depends on WHERE the bad script is loaded: `load("res://derived.gd")` outside `_init` exits cleanly in ~4s; `load(...).new()` inside a `-s` script's `_init` aborts `_init` before it installs a main loop, so the SceneTree spins forever with nothing to do (exit 124 under `timeout`, ~1% CPU) — this is the documented third class (an `_init` abort), just triggered here by a return-type mismatch instead of a bad dict key. Verified 2026-08-22: a mismatched return type hung for >10 minutes with no output; no completion time or CPU figure was measured for the fixed case. The fix is the third class's fix: read the run's own stdout/stderr first — the diagnosis is sitting right there, just easy to scroll past. `godot --headless --path . --check-only -s res://<script>.gd` reproduces the parse error in isolation, but it **exits 0 even on the parse error**, so it cannot be used as a blind gate.
- **A WARM-but-STALE `.godot` fails art tests on OLD PIXELS, and the red accuses the wrong thing.** The `cp -R .godot` trick above starts a worktree warm — but that cache is a snapshot. Merge in (or regenerate) a changed PNG afterwards and Godot keeps serving the *previously imported* texture: `Art.tex()` reads `.godot/imported/*.ctex`, not the PNG on disk. A test asserting the new art then fails while the working tree is completely correct — verified 2026-07-25, when a regenerated reticle merged with a byte-identical sha to its branch and its own test still reported "no E tick at radius 12", because the cache was stamped 33 minutes before the art. **Trusting that red means "fixing" a correct asset.** Before touching art a test complains about, compare `ls -la .godot/imported/<name>.png-*.ctex` against the PNG's mtime, and re-run `--import`. Note `--import` only re-imports what it thinks changed, and it is cheap — run it after ANY merge that touches `assets/`.
- **Parallel worktrees SHARE `user://` — it is keyed on project name, not on path. Run `tools/run_tests.sh` instead of raw `godot` when anything else may be running.** Every worktree of this project reads and writes the same `~/Library/Application Support/Godot/app_userdata/Commander In Chief/` (the folder is `config/name` from project.godot, verbatim — spaces and all; the pre-rename `Project Ikari/` dir is still sitting next to it), so concurrent runs fight over one `ikari_best.cfg` *and* one `logs/godot.log`. Two failure modes, both seen repeatedly: a sibling Godot rotates the log away and the engine-error gate fails a clean diff with "no log carried this run's marker"; and the save/settings tests (`test_robustness.gd`, `test_menu_layout.gd`) stash and restore the REAL config, so concurrent runs corrupt each other's fixtures. Confirmed against the Godot docs: the path derives from the project name and `application/config/use_custom_user_dir` — both *project settings*, so there is no per-run CLI override (`--help` has no `--user-data-dir`). The one per-process lever is `HOME` (macOS `~/Library/Application Support/…`, Linux `$XDG_DATA_HOME` or `~/.local/share/…`) — **verified empirically 2026-07-25**, not just from the docs. Copying the Godot binary does **not** help — the binary is not the shared state.
  - **`tools/run_tests.sh`** is that lever, and nothing more: a ~20-line wrapper that runs `godot --headless --path <repo>` under a fresh `mktemp -d` HOME (XDG_* cleared), then deletes it. Default args are `-s res://tests/run_tests.gd`; pass your own to run any headless script (`-s res://tools/smoke.gd`), `SUITE=` still works, `GODOT=` overrides the binary. It fails closed if the redirect did not take, and it **also owns the shutdown-leak gate**: Godot prints `N ObjectDB instances were leaked` / `RIDs of type … were leaked` / `ERROR: N resources still in use at exit` only on the process's *stdout*, after the file logger is gone, so `run_tests.gd::_gate_engine_errors` (which reads `user://logs`) structurally cannot see them — this wrapper and `ci.yml` are the only two places that can. It is gated at **zero, with no floor**. ⚠️ Two different causes print those same lines: a `Node` subclass allocating `Node` members at *declaration* and only `add_child()`ing them in `_ready()` (they orphan when freed outside a SceneTree — the headless-test case), **and** audio still playing at `quit()` (the AudioServer is torn down *after* `ObjectDB::cleanup`, so live streams count as leaks). Run with `--verbose` to tell them apart: only-`AudioStream*` classes means the second. The three gated tools that boot `src/main.tscn` — `smoke.gd`, `e2e_playthrough.gd`, `perf_probe.gd` — therefore end with `await Quiesce.teardown(self, main)` (`tools/quiesce.gd`): it disables processing *first*, silences every player, then waits in **wall time** (the release happens on the audio thread, so idle frames are the wrong unit). Add that call to any new tool this gate will see. The other FOUR `main.tscn` bootstraps — `screenshots.gd`, `biome_capture.gd`, `probe_concussion_hud.gd`, `gif_capture.gd` — do **not** free their main and still leak (measured: `screenshots.gd` prints 2 leaked ObjectDB instances); they are GL-only capture tools run by hand, outside CI and outside `run_tests.sh`, so nothing gates them today — that is a known gap, not a passing state. Measured: `e2e_playthrough` 30 leaked objects + a retained `cmd_levelstart_6.mp3` → 0, `smoke` 2 → 0, `perf_probe` 2 → 0, each on 6-of-6 runs. **Verified:** two full suites run concurrently both PASS; the engine-error gate still goes red on a planted `push_error`; the real `user://` is byte-identical (mtime+size) across save/settings runs.
  - It does **not** solve: CPU contention (parallel Godots still starve each other — the "hanging suite" above), the shared `.godot` import cache of a *single* worktree, or anything about the *real* save file when you actually want to play the game. And it is not a substitute for the gate — a run with no private HOME (plain `godot …`) is still exposed.
  - ⚠️ The HOME dir must be **canonical**: macOS `$TMPDIR` ends in a slash, so a raw `mktemp` path carries a `//`, and Godot's `DirAccess.open("user://…")` then silently hands back the PROJECT dir instead (its root-path check compares against the realpath byte-for-byte and, on mismatch, falls back to the CWD). That reads as the very "no log carried this run's marker" failure the script exists to remove. The `pwd -P` in the script is load-bearing — don't "simplify" it away.
- **Dev-only autoloads must never ship.** The godot-mcp editor plugin re-adds an `[autoload] MCPGameBridge` entry to `project.godot` whenever the editor runs with the plugin enabled. It targets untracked `addons/godot_mcp/`, so exported builds spam "Failed to instantiate an autoload". It has regressed once already; `test_assets.gd::test_no_dev_addon_references_in_project_godot` now fails on **any** line of `project.godot` referencing `addons/`, in any section — the earlier `[autoload]`-only version let the plugin's `[editor_plugins] enabled=…` line through. Don't commit the re-addition.
- **CI is live**: `.github/workflows/ci.yml` runs a 3-OS matrix (Linux · macOS-arm64 · Windows) that imports, boot-smokes (`tools/smoke.gd`), and runs the full golden-checksum suite, failing on any `SCRIPT ERROR` or a missing `PASS` line. A separate `lint` job runs `tools/lint_sim.gd` (the no-floats/no-RNG/no-`Time`/no-scene-tree gate), `tools/lint_assets.gd` (asset .import sidecars), and `python3 tools/i18n_check.py` (locale .po sync and string extraction). The Godot version is pinned in `tools/versions.lock`. Still run the suite locally before pushing — CI is the backstop, not the first check.
- **The blocking test gate is timing-free.** `test_perf.gd` asserts wall-clock microseconds per tick and is therefore in `run_tests.gd`'s `OPT_IN_SUITES` — skipped by the default full run, run explicitly via `SUITE=perf` (CI does that in an advisory `continue-on-error` job). Noisy shared runners made it fail for reasons unrelated to the commit, and a randomly-red gate stops being read.
- **Boot-smoke's exit code proves nothing on its own.** With `src/main.gd` failing to *parse*, `main.tscn` still instantiates and `tools/smoke.gd` still prints `SMOKE OK` and exits 0 — CI greps the log for both the sentinel *and* `SCRIPT ERROR` for exactly this reason.
